Product design:

- Use `product.experience` as the initial art direction when present. Turn it into a coherent working product, and improve it when the actual content calls for a better choice. Match composition, typography, density, color, and interaction structure to the domain; changing only an accent or headings does not establish a distinct product. Shared components supply reliable behavior and CSS defaults, not a prescribed page layout. Product CSS takes precedence over the foundation. Keep technical delivery details out of identity and ordinary task copy.
- Use a concise, believable product name from `product.experience` or the idea; pass it as the `AppShell` title when using that component. `PRODUCT_NAME` carries the proposed name or a shortened fallback; never use the full summary as a heading. Use at most one short utility subtitle. No "Local workspace", implementation commentary, landing-page hero, invented statistics, or decorative feature cards.
- Make the first screen useful: the primary collection/workflow, its current state, and one obvious next action. Choose a layout for the job: readable rows for record tracking, grouped state views for workflow work, a browsable catalog with a clear cart for commerce. Do not introduce a separate dashboard or navigation unless it helps the actual required tasks.
- Use `AppShell`, `SectionHeader`, `EmptyState` and `StatusMessage` where useful. Provide an actionable empty state and a distinct no-filter-results state. Distinguish destructive actions visually and keep the required create/edit/state-change actions direct. Surface success next to the working area with `role="status"`; errors use `FieldError` or `StatusMessage tone="error"`. Keep entered values when validation fails.
- For repetitive synchronous create/edit/action forms, optionally use `RecordForm` from `../system/record-form`. Its field values are strings; your domain callback parses and validates them and returns `{ ok: true }` or `{ ok: false, errors: { fieldKey: message } }`. The helper preserves failed drafts, scopes labels/errors, and resets only with `resetOnSuccess`. Use `key={record.id}` when switching edited records. Form/field-grid/action classes and surrounding layout remain yours. Native custom forms are equally valid for interactions that do not fit this helper.
- When `../system/collection-controller` is materialized, optionally use it for one flat local collection of string-valued records. Export a module-scope `CollectionDefinition` from `domain.ts`: stable `storageKey`, noun/title field, editable field descriptors, defaults including hidden state, pure field `validate`, complete-record `validStored`, and guarded actions returning patches or errors. In `App`, `useCollection(definition)` owns canonical records, persistence, editor and notices; render your own domain-specific rows, board, filters, counts and actions from its returned values. `CollectionEditor` is an optional accessible form; position and style it to fit the task, and render `controller.notice` visibly. No extra persistence effect is needed. Use custom domain/React state for transactions, relations, non-string data or unsuitable interactions. This helper supplies behavior, never a common page layout.
- The linked base stylesheet already styles all native controls and exports these reusable classes: `workspace-layout` (main + aside, stacked on mobile), `workspace-main`, `workspace-aside`, `toolbar`, `filters`, `form-grid`, `field`, `form-actions`, `record-list`, `record-row`, `record-title`, `record-meta`, `row-actions`, `record-grid`, `table-scroll`, `status-badge`, `metric-inline`, `button-primary`, `button-ghost`, `button-danger`, `sr-only`. A `status-badge` can use `data-tone="success|accent|error"`. Build on this foundation with compact product-specific CSS instead of rewriting controls, resets, or a whole design system.
- In `styles.css`, establish the product's composition, typography and coherent palette using the supplied Foundation design API. Set page, surfaces, text and action colors together; `--on-accent` controls text on primary actions. Maintain readable contrast and visible keyboard focus. Use system fonts and CSS; no remote fonts, image URLs, network assets or icon packages. Keep headings compact, secondary text readable, tap targets at least 44px, and filters/actions wrapping. At 390px, adapt the working area and group related actions efficiently rather than making every button a separate full-width row; use `table-scroll` when appropriate and keep required actions accessible. Respect `prefers-reduced-motion`.

When calling a generic transaction helper with both success and error return branches, provide explicit state and success-value type arguments. This prevents TypeScript from inferring the success value as optional.

Give every visible control a unique contextual accessible name when creation, editing, filtering, or checkout reuse the same concept. Entry forms must submit with the keyboard as well as their button. Show validation as an error and reserve success feedback for completed changes. In tests, scope repeated controls to their form, card, row, or region with `within`; never rely on an unscoped singular query when multiple matching elements are valid. BLOCK-owned setup cleans the DOM and browser storage between tests and restores Vitest spies/global stubs. Use real storage by default; persistence survives unmount/remount within one test. For storage failures use `vi.spyOn(Storage.prototype, "setItem")`; instance method assignments do not reliably replace JSDOM Storage methods.

`App` must render safely as `<App />`. Export the component; the linked `main.tsx` owns `createRoot` and mounting, so do not mount React inside product code. Create default repositories, providers, arrays, objects, and callbacks at module scope or stabilize them with `useState` or `useMemo`; never create a default object or function in the component parameter list when an effect depends on it.

The repository-backed state owned by `App` is canonical. Successful domain workflows must apply their complete resulting state to that owner so persistence observes the same products, records, counts, cart, and orders shown by the UI. Save the complete next state successfully before publishing it in React. Catch storage exceptions, show an error, and retain previous records and entered values for retry; failure tests must assert that unsaved changes were not committed. Do not leave committed results only in child-component state, and do not dispatch a custom event unless an active parent listener applies its payload. Failed or declined workflows must leave canonical state unchanged.

Keep `product.test.tsx` focused with reusable setup helpers. Every acceptance journey must have an executed test whose full name includes its exact identifier in square brackets, for example `it('[journey_add] adds a record', ...)`. A test may name multiple exact `[journey_id]` tags only when its assertions cover each tagged journey. Untagged, missing, skipped or failed tests cannot establish a passing journey. Prefer domain-function tests for rules and observable UI journeys for complete interactions. Exercise nondefault field values and assert they are preserved, along with counts or related state changed by the same journey. Keep coupled steps in one journey connected through real resulting state. Never query `role="form"` unless the form has an explicit accessible name. Never use a broad singular `getByText` when the same wording can legitimately occur in an option, status, notice, or card. For validation, locate the relevant field or region and assert the corresponding alert's text content; do not query an alert by accessible name.

Do not use external services, network calls, authentication, or package installation unless the ProductSpec explicitly requires them. Do not merely describe the implementation: finish by writing all four AGENT-owned files.
