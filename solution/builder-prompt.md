Product design:

- Use `product.experience` as the initial art direction when present. Turn it into a coherent working product, and improve it when the actual content calls for a better choice. Match composition, typography, density, color, and interaction structure to the domain; changing only an accent or headings does not establish a distinct product. Shared components supply reliable behavior and CSS defaults, not a prescribed page layout. Product CSS takes precedence over the foundation. Keep technical delivery details out of identity and ordinary task copy.
- Keep brand decoration coherent: prefer a restrained signature accent and neutral palette while preserving meaningful status/data colors and explicit user design choices. Family references are adaptable suggestions. Keep ordinary text, including button labels, at least 4.5:1 contrast and controls/focus states visible. Realize the direction through `:root` overrides in `src/product/styles.css`; if none is supplied, choose one from the product's purpose and content.
- Use a concise, believable product name from `product.experience` or the idea; pass it as the `AppShell` title when using that component. `PRODUCT_NAME` carries the proposed name or a shortened fallback; never use the full summary as a heading. Use at most one short utility subtitle. No "Local workspace", implementation commentary, landing-page hero, invented statistics, or decorative feature cards.
- Make the first screen useful: the primary collection/workflow, its current state, and one obvious next action. Choose a layout for the job: readable rows for record tracking, grouped state views for workflow work, a browsable catalog with a clear cart for commerce. Do not introduce a separate dashboard or navigation unless it helps the actual required tasks.
- Use `AppShell`, `SectionHeader`, `EmptyState` and `StatusMessage` where useful. `AppShell` has an optional `mark` for a product-specific symbol; a strong product name can stand alone. Provide an actionable empty state with its copy and action grouped together, and a distinct no-filter-results state. Distinguish destructive actions visually and keep the required create/edit/state-change actions direct. Surface success next to the working area with `role="status"`; errors use `FieldError` or `StatusMessage tone="error"`. Keep entered values when validation fails.
- For repetitive synchronous create/edit/action forms, optionally use `RecordForm` from `../system/record-form`. Its field values are strings; your domain callback parses and validates them and returns `{ ok: true }` or `{ ok: false, errors: { fieldKey: message } }`. The helper preserves failed drafts, scopes labels/errors, and resets only with `resetOnSuccess`. Use `key={record.id}` when switching edited records. Form/field-grid/action classes and surrounding layout remain yours. Native custom forms are equally valid for interactions that do not fit this helper.
- When `../system/collection-controller` is materialized, optionally use it for one flat local collection of string-valued records. Export a module-scope `CollectionDefinition` from `domain.ts`: stable `storageKey`, noun/title field, editable field descriptors, defaults including hidden state, pure field `validate`, complete-record `validStored`, and guarded actions returning patches or errors. In `App`, `useCollection(definition)` owns canonical records, persistence, editor and notices; render your own domain-specific rows, board, filters, counts and actions from its returned values. `CollectionEditor` is an optional accessible form; position and style it to fit the task, and render `controller.notice` visibly. No extra persistence effect is needed. Use custom domain/React state for transactions, relations, non-string data or unsuitable interactions. This helper supplies behavior, never a common page layout.
- The linked base stylesheet already styles all native controls and exports these reusable classes: `workspace-layout` (main + aside, stacked on mobile), `workspace-main`, `workspace-aside`, `toolbar`, `filters`, `form-grid`, `field`, `form-actions`, `record-list`, `record-row`, `record-title`, `record-meta`, `row-actions`, `record-grid`, `table-scroll`, `status-badge`, `metric-inline`, `button-primary`, `button-ghost`, `button-danger`, `sr-only`. A `status-badge` can use `data-tone="success|accent|error"`. Build on this foundation with compact product-specific CSS instead of rewriting controls, resets, or a whole design system.
- In `styles.css`, establish the product's composition, typography and coherent palette using the supplied Foundation design API. Set page, surfaces, text and action colors together; `--on-accent` controls text on primary actions. Maintain readable contrast and visible keyboard focus. Use system fonts and CSS; no remote fonts, image URLs, network assets or icon packages. Keep headings compact, secondary text readable, tap targets at least 44px, and filters/actions wrapping. At 390px, adapt the working area and group related actions efficiently rather than making every button a separate full-width row; use `table-scroll` when appropriate and keep required actions accessible. Respect `prefers-reduced-motion`.

When calling generic transaction helpers, provide explicit state and success-value type arguments; `TransactionStore<State>.update<Value>` and `.commit<Value>` only need the success-value argument. A rejected branch returns `{ error: message }`, never a partial success value. Enforce required numeric rules in the domain: finite values, integer quantities for indivisible units, and bounds. Input min/max/step attributes alone do not validate a transaction; test invalid quantities and more than one distinct record through the UI.

Give every visible control a unique contextual accessible name when creation, editing, filtering, or checkout reuse the same concept. Entry forms must submit with the keyboard as well as their button. Show validation as an error and reserve success feedback for completed changes. In tests, scope repeated controls to their form, card, row, or region with `within`; never rely on an unscoped singular query when multiple matching elements are valid. BLOCK-owned setup cleans the DOM and browser storage between tests and restores Vitest spies/global stubs. Use real storage by default; persistence survives unmount/remount within one test. For storage failures use `vi.spyOn(Storage.prototype, "setItem")`; instance method assignments do not reliably replace JSDOM Storage methods.

`App` must render safely as `<App />`. Export the component; the linked `main.tsx` owns `createRoot` and mounting, so do not mount React inside product code. Call hooks only at the top level of a component or custom hook, never in a loop, mapped row, condition or event handler. For repeated controls use stable record-derived IDs or a separate row component; changing the record count must not change hook order. Create default repositories, providers, arrays, objects, and callbacks at module scope or stabilize them with `useState` or `useMemo`; never create a default object or function in the component parameter list when an effect depends on it.

Use one canonical state owner. For local transactional products, prefer `TransactionStore<State>` from `../system/transaction`, backed by `LocalStorageRepository<TransactionEnvelope<State>>` whose validated fallback is `{ state: initialState, completedKeys: [] }`. Construct the store once per App with a lazy `useState` initializer; initialize the React view from `store.state`. Use `store.update<Value>(prepare)` for repeatable create/edit/delete/cart changes; each call can save a new change without an idempotency key. Use `store.commit<Value>(intentKey, prepare)` only for a once-per-intent operation such as checkout: retain the same key while retrying that intent and use a new key for a genuinely new checkout. Never use permanent operation labels or a record ID as the key for ordinary repeatable edits. Inside either synchronous `prepare(snapshot)` callback, revalidate mutable preconditions (stock, capacity, balance, workflow state) against that latest snapshot before producing the complete next state. Reject invalid operations with `{ error }`; never clamp an invalid deduction into apparent success. For simulated payments, call the supplied synchronous `simulatePayment` here and return its error on decline. The existing async payment-provider API remains available; do not pass an async callback to this synchronous store.

`transact` and `transactOnce` prepare candidates only; their `ok` does not prove a save. `TransactionStore.update` and `.commit` return `ok: true` only after saving the whole envelope, preserving existing completion keys. On success, publish `result.envelope.state` to React, then reset/close forms and show success. On failure, keep entered values and canonical state, clear stale success feedback, and show the error in the active view. Never hide the return value behind a void persistence wrapper or show success after a failed save. Apply the same commit-before-feedback boundary in custom state code. Test repeated ordinary saves, a rejected current-state precondition, and a failed save followed by retry through the visible UI when applicable; assertions must cover related state and absence of false success, not merely that an error exists.

Keep `product.test.tsx` focused with reusable setup helpers. A test may name multiple exact `[journey_id]` tags only when its assertions cover each tagged journey. Untagged, missing, skipped or failed tests cannot establish a passing journey. Prefer domain-function tests for rules and observable UI journeys for complete interactions. Exercise nondefault field values and assert they are preserved, along with counts or related state changed by the same journey. Keep coupled steps in one journey connected through real resulting state. Never query `role="form"` unless the form has an explicit accessible name. Never use a broad singular `getByText` when the same wording can legitimately occur in an option, status, notice, or card. For validation, locate the relevant field or region and assert the corresponding alert's text content; do not query an alert by accessible name.
